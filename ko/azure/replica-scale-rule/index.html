스케일업과 스케일다운이 반복되던 이유

Doosan published on October 29, 2026
9 min, 1735 words

Categories: post

Tags: azure container-apps scaling performance

두 편 중 2편이다. 1편은 새 레플리카의 준비 비용을 사용자 대신 앱이 치르게 했다. 첫 사용자 요청 p50은 7.5초에서 1.3초가 됐다. 레플리카가 태어나는 횟수는 줄지 않았다. 평일에도 하루 60~90개가 뜨고, 수명 중앙값은 7.5분이었다. 근본적인 해결은 그 회전을 멈추는 것이다.

회전을 만든 것은 부하가 아니었다. 스케일 규칙을 적지 않아서 플랫폼의 기본 HTTP 규칙이 돌고 있었고, 그 규칙의 기준값은 문서에 없다. 운영 수치는 문서에 적힌 계산식과도 맞지 않았다. 규칙을 AppHost에 명시하고, 동시 요청 50, 최대 3개로 두었다. 배포할 때마다 컨테이너 앱이 다시 만들어지므로, 포털에서 바꾼 값은 다음 배포가 지운다.

1. 1편 다음에 남은 것

워밍은 2026-10-02부터 돌았다. 그 뒤 일주일(10-01~10-08 기준선과 겹치는 구간)을 다시 보면, 태어난 지 2분이 안 된 레플리카의 요청은 26.7%가 1초를 넘었다. 2분이 지난 뒤는 3.2%였다. 첫 요청을 1.3초로 줄여도, 레플리카가 식기 전의 창은 남아 있다.

더 잘 보이는 경로는 HTTP가 아니다. 새 레플리카는 컨테이너가 시작된 뒤 약 4초 만에 RabbitMQ 소비자로 붙는다. 그때 집어 간 인바운드 메시지는 화면에 6~8초 뒤에 도착했다. 같은 시각, 이미 떠 있던 레플리카가 처리한 메시지는 1초 안쪽이었다.

그래서 1편의 합격은 그대로 두고, 질문을 바꿨다. 준비 비용을 누가 치르느냐가 아니라, 평범한 낮 동안 레플리카를 왜 수십 번 만들고 지우느냐다.

2. 규칙이 없었다

Aspire가 만든 컨테이너 앱에는 minReplicas: 1만 있고 스케일 규칙은 없었다. 규칙이 없으면 Container Apps는 기본 규칙을 적용한다. Scaling in Azure Container Apps의 기본 규칙 표는 트리거가 HTTP이고, 최소 0개, 최대 10개다. 우리는 최소를 1로 적어 두었으니 범위는 1~10이다.

시스템 로그에는 규칙이 null인데도 scaled to N by the scaler: http-scaler가 찍힌다. 기본 HTTP 규칙이 실제로 동작하고 있다는 뜻이다.

문서가 말하는 동작은 이렇다.

  • 스케일업 안정화 창은 0초, 스케일다운 안정화 창은 300초다. 늘어나는 것은 바로, 줄어드는 것은 5분 뒤다.
  • HTTP 규칙을 직접 정의하고 concurrentRequests를 생략하면 기본값은 10이다. 계산은 15초마다, 지난 15초의 요청 수를 15로 나눈 값이다. 그 값이 기준을 넘으면 레플리카를 하나 더 둔다.
  • 30초 폴링 간격에는 "HTTP와 TCP 규칙에는 적용되지 않는다"는 단서가 붙어 있다.

기본 규칙 자체의 동시 요청 기준값은 이 문서 어디에도 없다. 표의 10은 최대 레플리카 수다. concurrentRequests의 10은 규칙을 직접 정의하면서 값을 빼먹었을 때의 기본값이다. 2026-10-28에 공식 문서와 중국어 판, 스케일링 튜토리얼을 찾아도 기본 규칙의 기준값을 적은 문장은 없었다.

3. 문서의 계산식이면 늘어나지 말았어야 했다

p50과 p99는 요청이 1건 이상 있던 구간만 넣은 값이다.

4. 문서에 적힌 것, 관측된 것, 추론

셋을 섞으면 기준값이 10인 것처럼 말하고 끝나 버린다. 나눠 둔다.

문서에 적힌 것

  • 규칙이 없으면 기본 규칙이 적용되고, 트리거는 HTTP다.
  • 기본 규칙의 동시 요청 기준값은 문서에 없다.
  • HTTP 규칙을 정의하면서 concurrentRequests를 생략하면 10이다.

관측된 것

  • 규칙이 비어 있는데도 http-scaler가 레플리카를 늘린다.
  • 문서 계산식으로 5.5인 날에 77번 늘어났다.
  • 전체가 13 정도일 때 5개까지 늘어났다.

추론

  • 기본 규칙도 10을 쓴다는 말은 간접 근거만 있다. 트리거가 HTTP라는 점, 생략 시 기본값이 10이라는 점, 스케일업 직전 중앙값이 12라는 점이다. 문장이 아니다.
  • 스케일러가 보는 값은 Azure Monitor에 없다. 레플리카 하나의 값이나 활성 연결을 본다는 추정은 azure-container-apps#536 쪽에 가깝다. 확인하지 못했다.
  • 처리 시간을 앱 로그로 복원했으므로 프록시가 보는 동시성보다 작을 수 있다. 방향은 같다. 더 길게 잡아도 40이 나오지 않는다.

기준값의 정확한 정체를 몰라도 결정은 할 수 있다. 적지 않은 규칙이 평범한 트래픽에 레플리카를 만들고 있고, 그 입력은 우리가 재는 요청 수와 같지 않다.

5. 새 레플리카는 느린 HTTP 서버만이 아니다

2026-10-28 20:56 KST 전후, 메시지가 늦게 들어온다는 보고를 한 건 따라갔다. 그 시각 레플리카는 이미 하나 떠 있었다. 최소 1개라서 0에서 깨어난 콜드스타트는 아니다.

직전 인그레스는 11:54~11:57에 분당 0, 8, 0, 22건이었다. 같은 날 자원도 한가했다. SQL CPU는 최대 1~5%(한 번 18%), 워커 3% 이하, RabbitMQ는 0.02 core에 메모리 210MB, SignalR 서버 부하는 약 12%에 연결 최대 53, Redis 메모리는 2%였다. 레플리카 워킹셋 최댓값이 매일 1.01~1.13GB로 1Gi 한도에 붙어 있긴 했다. 이번 지연과의 관련은 확인하지 못했다.

인바운드 네 건이다. 끝점은 웹훅을 받은 시각부터 수신 메시지를 브로드캐스트한 시각까지다. 콘솔 로그 시각이 1초 단위로 묶여 있어서 ±1~2초 오차가 있다. 메신저 쪽이 웹훅을 보낸 시각은 로그에 없다.

6~7초 건을 소비 레플리카 기준으로 쪼개면, 엔벨로프 처리 1초, 메시지 행 생성까지 다시 4초, 브로드캐스트까지 다시 1~2초다. 기존 레플리카에서는 같은 경로가 1초 안에 끝났다.

같은 24시간(10-27 12:20Z ~ 10-28 12:20Z)에 스케일업 87번, 스케일다운 97번, 새 레플리카 105개였다. 1편의 기준 주간은 스케일업 52~78번, 컨테이너 시작 60~90개다. 스케일업은 KST 01~07시에 0건이고 나머지 시간에 3~8건씩이다. 아직 신규 테넌트가 들어오기 전의 값이다.

회전 비용은 HTTP 응답에만 있지 않다. 새 레플리카가 경쟁 소비자로 붙는 순간부터 받은 편지함의 지연으로 보인다.

6. 후보

후보판정
명시적 HTTP 규칙. concurrentRequests와 최대 레플리카를 배포 파라미터로선택. 규칙을 하나라도 정의하면 기본 규칙이 빠진다. 값은 환경 변수라 코드 수정 없이 바꾼다
기본 규칙을 두고, 테넌트가 늘면 다시 본다2026-10-09의 결정이었다. 10-28에 회전이 메시지 지연으로 보여서 10-29에 뒤집었다
최소 2개만 올린다기각. 기본 규칙이 남는다. 2개 위로의 회전은 닷새에 241번이었다
최소 2개에 CPU 규칙기각. 기동 첫 1분의 레플리카는 요청 0~25건인 분에도 2.6%가 CPU 80%를 넘었다. 배포로 두 개가 같이 뜨면 평균이 기준을 넘을 수 있다. 플랫폼이 기동 CPU를 빼는지는 문서에 없다
최소 2, 최대 2기각. 회전은 없어지지만 테넌트가 늘어도 커지지 못한다
포털이나 CLI로 규칙을 넣는다기각. 다음 배포가 컨테이너 앱을 다시 만들며 스케일 블록을 덮어쓴다

최소를 올리는 쪽이 먼저 떠오른다. 1개와 2개 사이를 오가는 횟수는 없어지기 때문이다. 그 선택지는 문서에 없는 기준값을 그대로 두고, 2개 위의 회전도 그대로 둔다. 관측된 확대는 2개에서 멈추지 않고 8개까지 갔다.

7. 고른 것: 규칙을 코드에 적는다

배포 코드가 컨테이너 앱의 스케일 블록을 직접 쓴다. 최대 레플리카와 동시 요청 기준은 파라미터다.

app.Template.Scale.MaxReplicas = maxReplicas;
app.Template.Scale.Rules =
[
    new ContainerAppScaleRule
    {
        Name = "http-scaler",
        Http = new ContainerAppHttpScaleRule
        {
            Metadata = { ["concurrentRequests"] = concurrentRequests },
        },
    },
];

aspire publish가 만드는 블록은 이런 모양이다.

scale: {
  minReplicas: 1
  maxReplicas: int(chatapi_MaxReplicas)
  rules: [
    {
      name: 'http-scaler'
      http: {
        metadata: {
          concurrentRequests: chatapi_ConcurrentRequests
        }
      }
    }
  ]
}

최소는 Aspire가 넣는 1 그대로다. 규칙을 하나 정의하면 플랫폼 기본 규칙은 빠진다.

Integration, Staging, Production 모두 같은 값이다. concurrentRequests 50, maxReplicas 3.

  • 50은 이 24시간의 동시 처리 최대 27보다 위다. 오늘 본 부하보다 분명 무거울 때에만 두 번째 레플리카가 생겨야 한다.
  • 3은 규칙이 또 잘못 튀어도 회전이 멀리 가지 못하게 막는 뚜껑이다. 레플리카당 50이면 세 개는 측정된 최대의 두 배 정도를 담는다.

둘 다 용량 시험의 결과가 아니다. 측정하면서 움직일 시작값이다. 같은 HTTP 스케일러는 기준을 2000으로 적어도 이르게 늘어났다는 보고가 있다(Microsoft Q&A 2288688). 50이 잠잠할지는 운영 측정만 말한다.

값은 각 환경의 배포 파라미터로 넘어간다. 숫자를 바꾸려고 코드를 다시 넣을 필요는 없다. 로컬 배포는 그 환경의 설정 파일에 같은 두 값이 있어야 한다.

8. 이 결정이 하지 않는 일

  • 1편의 워밍을 대체하지 않는다. 배포를 하면 레플리카는 여전히 새로 태어나고, 부하가 기준을 넘으면 두 번째, 세 번째도 태어난다. 태어난 레플리카의 첫 파이프라인 비용은 소켓을 열기 전에 앱이 치른다. 워밍이 임시 조치인 이유는 효과가 없어서가 아니다. 업무시간 내내 반복되는 탄생을 막지 못하기 때문이다.
  • 새 레플리카의 소비 시점을 바꾸지 않는다. 컨테이너 시작 약 4초 뒤에 MassTransit 엔드포인트가 등록되는 것은 그대로다. 이 결정은 그 일이 일어나는 횟수를 줄인다.
  • 용량은 0.5 vCPU 레플리카 세 개에서 멈춘다. 기본 규칙 아래에서 운영은 8개까지 갔다. 테넌트가 늘어서 세 개로 부족하면 파라미터를 올리고 다시 배포한다.
  • 이 규칙도 잘못 튈 수 있다. 입력이 같은 스케일러다. 세 개에 붙어 있는 분이 생기는지 봐야 한다.
  • 생성하는 스케일 블록을 검사하는 테스트는 없다. 환경 변수가 정말 50과 3인지도 코드가 보장하지 않는다.

예전에 비용을 레플리카 10개 기준으로 적어 둔 기록이 있다. 그 기록은 고치지 않았다. 이제는 세 개가 상한이라는 뜻으로 읽으면 된다.

9. 무엇을 보고 합격으로 볼 것인가

배포 전에 기준을 적어 둔다. 비교 구간은 2026-10-01~10-08의 평일이다. 이 규칙은 2026-10-29에 들어갔고, 이 글을 쓰는 시점에는 그 평일 재측정이 아직 없다. 숫자를 미리 좋게 말하지 않는다.

지표이전 (10-01~10-08)목표
하루 컨테이너 시작60~90더 적다
레플리카가 2개 이상이던 분609~919더 적다
응답 p5024~42ms나빠지지 않는다
응답 p90169~912ms나빠지지 않는다

기준선은 신규 테넌트 유입 전이다. 테넌트가 늘면 요청 1건당으로 비교한다. 함께 볼 것은 세 개에 붙어 있는 분과, 레플리카당 CPU다.

1편에서 배포 전에 합격선과 표본 수를 정해 둔 것이 판정을 믿을 만하게 만들었다. 같은 방식으로, 이 글의 합격은 "규칙을 코드에 적었다"가 아니다. 평일에 컨테이너가 덜 태어나고, 응답이 나빠지지 않는 것이다.
